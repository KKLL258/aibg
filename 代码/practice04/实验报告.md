# Practice 04 终极全功能 Agent 开发实验报告

## 一、实验目的

本实验旨在通过整合前序实验的核心功能，构建一个完整的企业级智能 Agent 系统，实现从基础 LLM 调用到具备记忆、知识、行动三位一体的全功能智能助手。通过本实验，达到以下教学目标：

1. 理解 Agent 系统的分层架构设计，掌握短期记忆、长期记忆、外部知识、行动能力的四要素整合方法
2. 掌握 Function Calling 的高级应用，能够设计并实现多工具协同工作
3. 解决意图识别冲突等实际工程问题，提升 Agent 系统的鲁棒性
4. 理解并实现联网数据获取能力，使 Agent 具备实时信息获取能力
5. 通过模块化代码重构，建立大型项目的工程化思维

## 三、实验过程

### 3.1 问题分析与架构设计

在实验开始前，我们发现了原 practice04 存在的核心问题：

**问题1：功能碎片化**
- 每个 practice 只包含该次教学点，功能独立不协同
- 用户问天气，反而去搜索本地聊天历史
- 意图识别过于灵敏，误判率高

**问题2：缺少核心能力**
- 没有联网能力，只能回答训练数据内的知识
- 没有时间感知，LLM 不知道"现在是什么时候"
- 工具调用次数上限过低，复杂任务无法完成

**架构设计方案：**

```
┌─────────────────────────────────────────────────────┐
│                  终极全功能 Agent                   │
├─────────────┬─────────────┬─────────────┬───────────┤
│  短期记忆   │  长期记忆   │  外部知识   │  行动能力  │
│  上下文压缩 │  5W提取日志 │  RAG向量库  │  联网+文件 │
└─────────────┴─────────────┴─────────────┴───────────┘
```

### 3.2 关键问题的解决过程

#### 3.2.1 意图识别冲突修复

**现象：** 用户问"查询明天青城山天气"，系统错误触发本地历史搜索

**根因：** 搜索意图判断规则过于宽松，只有"是否表达了搜索的意思"

**修复方案：** 增加严格的判断规则

```python
判断规则：
1. 必须明确提到"聊天历史"、"聊天记录"、"历史记录"、"历史对话"才返回 YES
2. 查天气、查资料、问实时信息等，都返回 NO
3. 只是普通问题，返回 NO
```

#### 3.2.2 联网能力的标准化实现

采用与 Practice02 完全一致的 `curl_request` 实现：

```python
def curl_request(url: str, method: str = "GET", timeout: int = 30) -> dict:
    """
    【常用示例】
    - 天气图: curl_request("https://wttr.in/成都")
    - 天气JSON: curl_request("https://wttr.in/青城山?format=j1")
    """
    # 纯文本内容最大返回 20000 字符，支持完整的 ANSI 艺术图
    if "text" in content_type or content_type == "":
        max_content = 20000
```

**数据源限制发现与处理：**
- wttr.in 只支持县级以上城市
- 青城山等景区无气象站数据
- 在 System Prompt 中显式告知 LLM 数据源限制
- 提示 LLM："查青城山请用都江堰替代，并向用户说明"

#### 3.2.3 工具调用生态完善

| 工具名称 | 参数说明 | 触发场景 |
|---------|---------|---------|
| `get_current_datetime` | 无参数 | 询问时间日期 |
| `curl_request` | url, method, timeout | 所有需要联网的场景 |
| `anythingllm_*` 系列 | workspace_slug 等 | 知识库文档查询 |
| 文件操作 6件套 | directory, filename 等 | 文件系统操作 |

工具调用最大次数从 5 次调整到 15 次，支持复杂推理链路。

### 3.3 System Prompt 工程

**强制约束指令：**

```
重要指令：
1. 凡是需要获取实时信息、外部数据、最新天气的，
   **必须调用 curl_request 联网获取**，不要凭空回答
2. 凡是需要获取知识库信息的，必须先调用工具获取真实数据
3. 必须严格按照工具函数的参数格式调用
4. 执行工具后，用自然语言向用户总结执行结果
```

## 五、实验总结

### 5.1 教学成果总结

本次实验成功完成了从"碎片化教学演示"到"生产可用完整系统"的跃迁，实现了 01-04 所有教学点的完整整合。通过本次实验，我们验证了 Agent 开发的核心方法论：

**1. 能力分层架构是 Agent 可靠性的基础**
- 短期记忆（压缩）+ 长期记忆（5W日志）+ 外部知识（RAG）+ 行动能力（工具调用），四层架构缺一不可

**2. Prompt 工程 > 模型能力**
- LLM 不知道它不知道的事情（如数据源地理限制）
- 需要工程师在 Prompt 中显式写出所有边界条件和约束

**3. 意图识别是最容易踩坑的环节**
- 这是 90% 的"弱智" Bug 的来源
- 规则永远严格优于模糊判断

### 5.2 遇到的问题与启发

| 问题 | 启发 |
|------|------|
| wttr.in 地理覆盖限制 | 工具的能力边界必须让 LLM 知道，否则会产生幻觉 |
| 意图误判 | 模糊分类一定要加白名单，宁可少触发不要误触发 |
| 流式输出与工具调用冲突 | 工具调用阶段用非流式，最终回答用流式，体验最佳 |
| 工具调用次数限制 | 复杂推理链路远超预期，15次是合理下限 |

### 5.3 后续扩展方向

1. **工具编排能力**：支持多工具并行调用与结果聚合
2. **反思机制**：增加 self-correction 自我校验环节
3. **长上下文优化**：引入 Rerank 等检索后处理
4. **多模态能力**：扩展图片识别、代码解释器等高级工具
